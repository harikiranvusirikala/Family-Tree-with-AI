## Working agreement with the owner

- Before building a step, its BUILD_PLAN section must be detailed and agreed. The owner may expand it themselves (step 4); otherwise draft it there, with open questions, and ask (step 6). Check the plan's library claims in the installed `node_modules` source and record any deviation in that step's notes.
- Build one BUILD_PLAN step at a time. At the end of a step, stop: show the test results and a short "try this" list, and wait for the owner's OK. A bug the owner finds gets a test that reproduces it, checked to fail without the fix.
- After the OK: commit to a `step-N-<name>` branch. The sandbox blocks github.com, so the owner pushes it (CI runs and Vercel builds a preview) and merges to `main` after checking the preview. `main` deploys production. Before starting the next step, check that local `main` has the merge: `git fetch` is blocked too, but the owner's pulls update local `main` and `origin/main` (fast-forward with `git merge --ff-only origin/main` if only the latter moved).
- Changes the owner asks for outside the plan (the night theme, the tree font) follow the same routine on their own branch (`night-theme`), with a short BUILD_PLAN section after the step they follow and a Progress row marked `–`. When another session is working in the main checkout, the owner asks for a worktree (see Environment gotchas). The owner may also say to commit straight to `main`: then rebase the branch onto `main`, keep both sides of conflicts between independent changes (usually the BUILD_PLAN Progress table and sections), run the tests on the result, and fast-forward `main` from the main checkout.
- When a step settles a design question, update ARCHITECTURE.md (the relevant section and §15), FEATURES.md Decisions, this file, and the BUILD_PLAN Progress table in the same commit. BUILD_PLAN step sections describe the step; status lives only in the Progress table.
- When a step adds indexes, the owner runs `MONGODB_DB=familytree_preview npm run db:setup` and `MONGODB_DB=familytree npm run db:setup` in their terminal before merging.
- The AI chat model is `claude-haiku-5-5`, chosen by the owner to keep costs near zero. Don't switch models without asking.

## Environment gotchas (owner's machine)

- **Port binding is sandboxed.** The Claude Code sandbox on this machine blocks opening local ports, so `npm run build` (Turbopack spawns a worker on a port) and `npm run test:e2e` fail inside it with `Operation not permitted`. The owner allowlists them as `exact_match`, so run them exactly as written, on their own: no `cd …&&`, no `timeout` prefix, no `2>&1 | grep`, nothing chained. Anything else is a different command and runs sandboxed. Rarely the exact `npm run test:e2e` is refused anyway; try again later, or ask the owner to run it.
- **Some sites are blocked.** The network proxy refuses e.g. cloudinary.com, and the live site itself (so the smoke test and any check of production run in the owner's terminal or on GitHub). To check how a service's API works, read its official npm package's source instead: `npm pack <name>` into a new scratch folder under `/tmp`, unpack it, read it, and don't install or run it (step 7 did this for Cloudinary).
- **No Google Fonts.** The network proxy blocks `fonts.googleapis.com`, so `next/font/google` breaks the local build. The app uses the system font stack; self-host any font from an npm package instead.
- **Playwright browser.** Playwright's own browser download is blocked, so locally it runs against the installed Google Chrome (`channel: "chrome"` unless `CI`). CI installs Playwright's Chromium.
- **Slow npm.** Installs through the private registry mirror can take several minutes; use long timeouts.
- **Harmless warning:** `next build` reports that it "ignored package-lock.json in /Users/harikiran.v01". That's a stray lockfile in the home folder, outside the repo; ignore it.
- **MongoDB needs the allowlist too.** The sandbox blocks MongoDB's DNS SRV lookup and TCP connections, and allowing a domain doesn't help because the driver doesn't use the web proxy. `npm run db:ping`, `db:setup`, `seed` and `test:db` are allowlisted `exact_match` like build/e2e, so run them exactly as written. If one is refused, ask the owner to run it.
- **Claude Code's own `ANTHROPIC_*` variables.** This session (and every process started from it) has `ANTHROPIC_BASE_URL` and `ANTHROPIC_CUSTOM_HEADERS` pointing at Claude Code's gateway, and the Anthropic SDK reads them by default. The app's chat client is always given its key and address (`chatClient()`), the e2e web server gets them cleared, and `test:ai-live` deletes them. Never name an app variable `ANTHROPIC_API_KEY` (the chat's key is `CHAT_API_KEY`), and don't run the live check from here.
- **PATH comes from how VS Code was started.** Opened from the Dock, the extension's shell may get only `/usr/bin:/bin:/usr/sbin:/sbin`, so `npm` is "command not found" (it's in `/opt/homebrew/bin`). Prefixing `PATH=…` makes it a different command, so it runs sandboxed and fails. Ask the owner to quit VS Code and open it from a terminal (`code .`), or to run the command themselves.
- **Session environment = `.env.local` at startup.** This session's environment is loaded from `.env.local` when it starts. Node's `--env-file`, `process.loadEnvFile` and Next.js never override variables that are already set, so after the owner edits `.env.local`, the session must be restarted before commands see the change. Next.js also loads a `.env` file as a fallback for anything missing from `.env.local`. A git-ignored `.env` with values (from 2026-10-18) is there and the owner keeps it, so `next build` lists "Environments: .env.local, .env"; `.env.local` wins. Put new local settings in `.env.local`, and don't suggest deleting `.env`.
- **Parallel sessions use a worktree** (`EnterWorktree`, under `.claude/worktrees/`, which `.git/info/exclude` hides locally):
  - **Setup:** it starts without the git-ignored files. Copy `.env.local` in, and clone `node_modules` with `cp -cR "<main checkout>/node_modules" node_modules` (an APFS copy-on-write clone, about 1.5 minutes, instead of a slow `npm ci`). For `npm run dev` there, the owner stops any dev server on port 3000 first: Google sign-in only returns to `localhost:3000`.
  - **The isolation guard:** inside the worktree it refuses `git -C <main checkout>` and long chained or heredoc scripts that it can't verify. Use the Edit tool and plain single commands.
  - **Ports:** the allowlisted commands run as written from the worktree. But e2e always uses ports 3100–3102, so two sessions' `npm run test:e2e` can't run at the same time.
- **Never start `npm run test:e2e` while the owner may be running it** (or another session is): Playwright empties `test-results/` when it starts, so the other run's traces vanish and its tests fail with `ENOENT … .playwright-artifacts`. When this session's runs are sandboxed (`querySrv ECONNREFUSED`, or Turbopack's "binding to a port: Operation not permitted"), ask the owner to run it and wait for the result.
  - **Finishing:** `ExitWorktree` with `keep` returns to the main checkout, where `main` can be fast-forwarded. Afterwards, `git worktree remove` can leave the folder behind (`node_modules`, the `.env.local` copy); delete it, then `git worktree prune`.

## npm and the lockfile

- `.npmrc` sets `omit-lockfile-registry-resolved=true`, so `package-lock.json` has **no `resolved` URLs**. Locally npm installs from the mirror; Vercel and GitHub Actions use the public registry. After any install, `grep -c '"resolved"' package-lock.json` must print `0`. Never commit private registry hostnames.
- `.npmrc` also sets `legacy-peer-deps=false`, overriding the owner's global setting, so `npm ci` on CI accepts the lockfile. Fix peer conflicts with version changes, not `--legacy-peer-deps` or `--force`.

## Architecture invariants (from ARCHITECTURE.md; follow them as code is added)

- **One Next.js app is both UI and API.** Server-only code goes in `src/server/`. Pure tree logic goes in `src/tree/`, which runs in the browser and in unit tests with no I/O.
- **Each person is stored once; sheets are views.** A sheet stores only `rootPersonId`, `extraPersonIds` and optionally `hideChildrenOf` (one of the root's couples, whose children it leaves out: a mother's own sheet). `buildSheetView()` computes who is shown, using the §6 rules: ancestors, then descendants of every ancestor (not into the hidden couple's children), then partners (not partners' parents), then extras. Never copy people into a sheet. Deleted sheets keep a `deletedAt` and are absent everywhere (`toGroupTree`, `firstSheetId`, the planner); pinned sheets and a group's last sheet can't be deleted.
- **A union is a couple** (the ♥): 1–2 `partnerIds` plus `childIds`. A person is a child of at most one union. Unions map to GEDCOM `FAM` records.
- **Layout** goes through `layoutEngine` (`src/tree/layout/index.ts`, ELK.js). The ELK adapter groups partners into side-by-side blocks with fixed connection points, then re-packs siblings with no family of their own eldest first (ARCHITECTURE.md §7). Hearts are placed by the shared `placeUnions()`, never by an engine itself.
- **Single write path.** Manual edits, confirmed AI proposals and imports all become an `Operation[]` (§10, with temporary IDs like `new:1`) applied by `applyOperations(database, groupId, ops, actor)` in one transaction. Don't add other write paths.
- **Permissions:**
  - Every server action, route handler and data load checks the role itself: pages and some actions with `requireRole(groupId, minRole)`; most actions with `requireUser()` plus a repository function that calls `roleInGroup` itself (`applyGroupChanges`, `signPhotoUpload`, the member/invite/request functions), so database tests can call it as a Viewer; route handlers with `getUser()` (401) plus `roleInGroup`. Layouts don't re-run on every navigation, and server actions can be called directly, so a check in a layout isn't enough. A layout that loads data (the sheets layout) checks for itself; a page never relies on a layout's check.
  - Repository functions require `groupId`.
  - The role is read from the database on each request, never stored in the session.
  - "No access" looks identical whether or not a group exists.
  - Only Admins and the Owner grant access, by invite or access request.
- **The AI never writes.** Proposal tools collect operations and save nothing. The user confirms on a `ProposalCard`, and the confirmed batch goes through `applyChangesAction`, the same server action as manual edits, so it is re-validated and permission-checked there. Tools are filtered by role (Viewers get read tools only), and there is no delete tool.
- **Photos** go straight from the browser to Cloudinary under `groups/{groupId}/`. Store the Cloudinary `photoId` (public ID), not a URL; build URLs with `photoUrl()`.
- **Databases** live in one Atlas cluster: `familytree_dev` (local), `familytree_preview` (Vercel previews), `familytree` (production), plus a throwaway `familytree_test_<run-id>` per test run.

## Server and data layer (as built)

- `src/server/db.ts`: `getDatabase()` returns the app's shared, cached client and database (from `MONGODB_URI` / `MONGODB_DB`), connected; `lazyDatabase()` returns the same without connecting. `openDatabase(name)` opens a separate connection to a named database, for tests and scripts; they must close it, and scripts call `closeDatabase()`. A `Database` is `{ client, db }`: the client is needed for transactions.
- IDs: MongoDB documents use `ObjectId`; everything in `src/tree/` and every `Operation` uses 24-character hex strings. Conversion happens only in `toGroupTree` (`src/server/repositories/family.ts`: documents → `GroupTree`, without soft-deleted people or sheets; `loadGroupTree` is the query plus this, and `loadGroupState` returns every record, deleted people and sheets included, for planner dry runs) and in `planOperations` (refs → `ObjectId`). Use `toObjectId()` (`src/server/ids.ts`); it throws `InvalidIdError`, which callers treat as "not found".
- **Dates** (an owner request after the final check): a person's `birthMonth`/`birthDay` and `deathMonth`/`deathDay` beside the years, only together and with their year. `src/tree/years.ts` has `DATE_FIELDS` and `lifeDates()` (copy them wherever person fields are copied: `toGroupTree`, `operationsFromFamily`, imports, edits), `datesProblem()` (the rules, used by the planner and the person form), `formatDate`/`formatLife` ("12 Mar 1985") and `birthOrder()` (sorting, eldest first). Cards show `formatYears` unless selected; button names stay "Name, years". The person form hides the death's fields until "Has died" is checked; `readPerson` ignores them while it isn't.
- `applyOperations` (`src/server/operations/apply.ts`): zod (`schema.ts`), then load the group's records in a transaction, then the pure `planOperations` (`plan.ts`), then bulk writes. Throws `OperationError` with the failing change's `index` and its `reason` (the message without "Change N:"). It doesn't check permissions: its callers do (`applyGroupChanges`, and `createGroup` for the group's creator).
- Soft-deleted people stay in their couples (so Undo restores them fully), but the planner treats them as absent, exactly as `toGroupTree` shows them: a couple whose partners are all deleted isn't anyone's parents, and a new partner can take a deleted partner's place. New rules must keep the planner and `toGroupTree` agreeing, or the browser offers edits the server refuses.
- `operationsFromFamily()` turns `FamilyData` with its own ids into operations with `new:<id>` temporary ids. The seed, the e2e `sampleGroup` fixture, `test/planning.ts` and database tests use it; imports have their own `importOperations` (step 10).
- Database reads in pages go inside `<Suspense>` after `await connection()` (see `src/app/dev/tree/db/page.tsx`), so they happen at request time and never during the build. Pages that call `requireUser`/`requireRole` read headers, which already makes them request-time.

## Groups, roles and editing (as built, steps 5–6)

- Our own `groups` and `memberships` (not Better Auth's organization plugin). `src/server/roles.ts` (pure) has `RANK`, `MIN_ROLE` (the §8 table), `can(role, action)` and `NoAccessError`.
- `requireRole(groupId, min)` in `permissions.ts` = `requireUser()` + `roleInGroup()` from `repositories/groups.ts`, and returns `{ user, role, group }`. Pages: `requireRole(...).catch(noAccessToNull)`, then render `<NoAccess groupId={groupId} user={user} />` (identical for every no-access case; it offers Request access, step 8). Server actions return an error message instead. Never `catch` everything: `requireUser` redirects by throwing.
- Group pages follow `src/app/g/[groupId]/settings/page.tsx`: a `<Suspense>` boundary around an async component that awaits `params`, then `requireUser()`, then `requireRole()`. The sheets are drawn by the layout `src/app/g/[groupId]/s/layout.tsx` (same pattern), so the editor stays mounted while tabs change `[sheetId]` with `pushState`; the `[sheetId]` page itself renders nothing.
- Writes that need more than content operations in the same transaction use `parseOperations` + `applyInTransaction` (see `createGroup`). Don't write persons, unions or sheets any other way.
- Editing (step 6): forms build operations with the pure helpers in `src/tree/edits.ts` and send them to `applyChangesAction` (`src/app/g/[groupId]/actions.ts`), which calls `applyGroupChanges` (`roleInGroup(…, maintain)` + `applyOperations`) and `groupChanged`. New edit types: add a builder plus a unit test against the sample family (`test/planning.ts`), and a planner rule if needed. A name change goes through `editPersonOps`, which adds `renameSheetsOps` so the person's sheets still titled "<Name>'s family" follow; the assistant's `update_person` uses `renameSheetsOps` too, so any new way to rename someone should.
- The sheets page is the hub most features plug into: `GroupSheets` (`src/app/g/[groupId]/s/GroupSheets.tsx`) holds the group's whole `GroupTree` (loaded once by the sheets layout), computes the current sheet's view, and keeps `run(ops)`, which sends a batch to `applyChangesAction` and resolves to the new ids once the page shows the change. Around the canvas: `SheetTabs` (with `trailing`: the eye that hides photos, Export, Import…, Ask AI), `FamilyCanvas` (also exposes `captureRef` for the picture), and side panels on the right (`PersonPanel`, `CouplePanel`, `ImportPanel`, `ChatWidget`). A new feature on a sheet usually adds a trailing button and a panel here, and saves through `run`; below 1024 px the button also needs its `menuItems` (or `beforeMenu`) twin and the panel uses `panel.ts` (see Phones and tablets).
- The canvas is read-only unless given `actions` (`CanvasActions`: onPerson, onCouple, selectedId). Cards and hearts then render overlay buttons named "Jake Cruz, 1945 – 2022" and "Steve Cruz and Arham Chopra, married", which e2e tests click.
- Server actions live next to their page in `actions.ts`, take bound ids (`action.bind(null, groupId)`), and check the role themselves (see Permissions above). After changing a group (or later, its members or content), call `groupChanged(groupId)` from `src/server/group-changed.ts` before returning or redirecting. It revalidates `/dashboard` and the group's pages; otherwise Back/Forward and the header link show the pages the browser kept from before the change.

## Photos (as built, step 7)

- No Cloudinary SDK: `src/server/cloudinary.ts` signs requests itself (`signParams`: SHA-1 of the sorted `key=value` pairs plus the secret), builds upload tickets (`uploadTicket`) and deletes photos (`deletePhotos`, best effort, logged). Pass the settings in explicitly (`cloudinaryConfig()` in server actions and the layout), so tests never pick up the real `CLOUDINARY_*` from `.env.local`.
- Upload: `signPhotoUploadAction` → `signPhotoUpload` (`roleInGroup(…, maintain)`; the server picks the random public ID) → the browser posts the file to Cloudinary (`upload-photo.ts`) → `applyChangesAction(setPhotoOps(...))`. The planner refuses a photo outside `groups/{groupId}/`.
- Replaced or removed photos come back as `ApplyResult.unusedPhotoIds` (nobody in the group uses them, deleted people included), and `applyChangesAction` deletes them with `after()`. Any new write path that changes photos must do the same.
- `PersonPhoto` draws the round photo or initials for cards and the panel. The cloud name reaches it through `CloudNameContext`, given by the sheets layout; without it there are no photos or photo buttons. `PhotosHiddenContext` (the eye button in `GroupSheets`, an owner request after step 11) makes every `PersonPhoto` show initials, so new places that draw a person's photo must use `PersonPhoto` to respect it.

## Members, invites and access requests (as built, step 8)

- Collections `invites` and `accessRequests` (one record per person per group; its status changes), plus a read-only `users` type for Better Auth's users. Repository functions in `repositories/members.ts`, `invites.ts` and `access-requests.ts` check the actor's role themselves (`roleInGroup`) and throw `NoAccessError` or `MemberError` (a message for the person). Server actions add `requireUser()`, turn those into messages, and call `groupChanged(groupId)`.
- The rules are pure, in `src/server/members-rules.ts`: `normalizeEmail` (gmail dots and `+tags`), `maskEmail`, and who may change whom (`memberChangeProblem`, `transferProblem`, `leaveProblem`). Change them together with their unit table.
- "No access looks the same" now includes the no-access page's Request access and its outcomes. `accessState`/`requestAccess` must behave identically for real, made-up and deleted groups (requests for made-up groups are stored). Only someone holding an invite to the group sees something different.
- Requesters never see a group's name until they're in it (dashboard included). Member emails are shown only to Admins and the Owner.
- React 19 resets a `<form action>` after the action finishes, to each field's first default, and never updates a `<select>`'s `defaultValue` after it first renders. A dropdown that stays on screen after saving must be keyed by the saved value (see `MemberRow`), or it jumps back to its first value.
- A server component can't import plain values from a `"use client"` module (they become client references): shared strings live in plain modules such as `src/components/request-messages.ts`. Page files may only export what Next.js expects, so helpers like `shortDate` live in `src/components/`.

## AI chat (as built, step 9)

- `POST /api/chat` (`src/app/api/chat/route.ts`): `getUser()` (401), `chatConfig()` (503 without `CHAT_API_KEY`), `parseChatRequest`, `roleInGroup(…, view)` (one 404 for every no-access case), `countChatMessage` (429 at the daily limit), then `runChatTurn`, streamed as JSON lines (`ChatEvent`: text, tool activity, proposal, done with the turn, error).
- `src/server/ai/`: `config.ts` (settings and client), `tools.ts` (strict schemas, every field required and optional ones nullable; `toolsFor(role)`), `handlers.ts` (pure: lookups on the `GroupTree`, proposals dry-run with `planOperations` on the `GroupState`; temporary ids `new:1…`), `prompt.ts` (fixed system prompt, `rosterNote`, `proposalNote`), `chat.ts` (the loop), `request.ts`.
- **Append-only conversation.** Claude Haiku 5.5's thinking blocks are valid only while everything before them is unchanged, and the API rejects altered ones. Never put changing data in the system prompt or the tools, never edit or drop earlier messages or thinking blocks, and add new information as one `role: "system"` message right after the person's question (it must follow a user message). The browser keeps the conversation and sends it back unchanged.
- Claude Haiku 5.5: no `temperature` or prefill (400), effort default `medium`, no refusal fallback; read content blocks by type (a reply can start with an empty `thinking` block).
- The AI never writes: proposals come back as `pending` operations; the panel's Confirm calls `applyChangesAction`. New tools: add the schema, a handler with a unit test against the sample family, and a `describeOperations` line if it proposes something.
- The e2e stand-in `e2e/model-stub.mts` (port 3102, `CHAT_API_URL`) streams scripted replies in the API's SSE format, with signed thinking blocks, and refuses edited conversations or misplaced system messages like the API. `GET /calls` lists the tools, operator notes and last question of each request (`E2E_MODEL_URL`). Add scripted turns there for new chat tests.

## Import and export (as built, step 10)

- The converters in `src/server/import-export/` are pure (no `server-only`, no `mongodb`), because the browser runs them: `json.ts` (the app's own lossless format, zod-checked), `gedcom.ts` (GEDCOM 5.5.1), `import-plan.ts` (`findDuplicates`, `importOperations`: choices → operations with temporary ids `new:p0…`, `new:u0…`, `new:s0…`), `types.ts` (`ImportData`, `exportPart`: what one sheet exports, `MAX_IMPORT_PEOPLE`).
- Imports are parsed in the browser (`ImportPanel`), then saved as an ordinary batch: `applyChangesAction` into this group, `importGroupAction` (dashboard, `createGroup`) into a new one. There is no import route. Limits: 2,000 people per file and per batch (`operationsSchema`), 20,000 operations, 4 MB server action bodies (`next.config.ts`).
- Data export is `GET /api/groups/[groupId]/export?format=json|gedcom[&sheet=]` (Maintain and up; one 404 otherwise). The picture is captured in the browser (`sheet-picture.ts`, html-to-image): it removes the `dark` class from `<html>` and React Flow's element while it captures (an overlay hides the change), so new canvas styling must work through `dark:` classes or `useTheme()`, not hard-coded night colours.
- Round trips are the tests to extend: a new field in persons, couples or sheets must survive JSON export and import (and GEDCOM, where it can).

## Backups and hardening (as built, step 11)

- **Backup** (F12): `src/server/backup/` (no `server-only`; the scripts and tests use it). `archive.ts`: every collection except `NOT_BACKED_UP` (`sessions`, `verifications`), a header line (counts, indexes) then one canonical Extended JSON line per document, gzip; `restoreDatabase` refuses collections that hold records unless `replace`, counts before creating indexes (a TTL index could remove expired records first). `crypt.ts`: AES-256-GCM, `"FTB1" | IV | ciphertext | tag`, key = 32 bytes base64. Scripts: `scripts/backup.mts`, `scripts/restore.mts` (asks for the key without echoing it). `.github/workflows/backup.yml` runs nightly with the GitHub secrets `MONGODB_BACKUP_URI` (read-only user) and `BACKUP_ENCRYPTION_KEY`, trial-restores into a `mongo:8` service container, and uploads `backups/` as a 90-day artifact. A new collection is backed up automatically; a new temporary one with credentials belongs in `NOT_BACKED_UP`. The service container has no health check on purpose: one running `mongosh` never reported healthy on GitHub's runner, and the restore's driver waits up to 30 s for the server.
- **GitHub Actions workflows can't run from here.** A workflow change is tested by the owner: push its branch, then Actions → the workflow → Run workflow, picking that branch (it runs the branch's file). Schedules run only from `main`.
- **Security headers:** `securityHeaders(env)` in `src/server/security-headers.ts`, applied to every path by `next.config.ts` (also `poweredByHeader: false`). The CSP is fixed at build time, allows inline scripts (no nonces: they'd need every page drawn per request, which `cacheComponents` doesn't allow), and lists Cloudinary: `res.cloudinary.com` for images and connections, the API (`CLOUDINARY_API_URL`, or the e2e stand-in) for connections. A feature that loads anything from another origin must add it there, with its unit test; `next dev` adds `'unsafe-eval'`.
- **Every e2e test fails on a CSP violation** (the auto `policyViolations` fixture in `e2e/fixtures.ts` watches `page` and every page given to `signIn`). A test that expects one clears the array (see `e2e/security.spec.ts`).
- `test/server-checks.test.ts` reads every `"use server"` file and route handler (TypeScript's parser) and fails if an exported function doesn't call `requireUser`, `requireRole` or `getUser`, directly or through a function in the same file. It also forbids inline `"use server"` inside components. Better Auth's route is exempt.
- **Server action arguments are untrusted values of any shape,** including objects: bound ids too. Turn ids into `ObjectId`s with `toObjectId` (it rejects non-strings) and check any other string that goes into a query (`isInviteToken`) before querying; `{ $ne: "" }` must never reach MongoDB.
- Better Auth stores Google's tokens encrypted (`account.encryptOAuthTokens`).
- **Smoke test:** `smoke/production.spec.ts` with `playwright.smoke.config.ts` (no web server, `SMOKE_URL` or production). `smoke.yml` passes the repository variable `SMOKE_URL` (empty when unset, so the config uses `||`). Signed out only: never sign in or write to production from it. `.github/workflows/smoke.yml` runs it on Vercel's successful `Production` deployment statuses and by hand.
- Accepted risks are in ARCHITECTURE.md §11, including open sign-up: any Google account can sign in and create groups, kept by the owner's choice (§15).

## Phones and tablets (as built, after the final check)

- Tailwind's breakpoints: phones below `md` (768 px), tablets below `lg` (1024 px). Computers (`lg` and up) keep the original layout, which every desktop e2e test checks. Prefer CSS (`md:`/`lg:` classes, rendering both versions where they differ). The JS checks `isPhone()` and `isTabletOrPhone()` (`src/components/screen.ts`) only run in effects and event handlers: server rendering doesn't know the screen.
- **The sheet row:** below `lg`, `trailing` is hidden and `SheetTabs` shows `beforeMenu` (the eye, `HidePhotosButton`) and the ⋯ "Sheet menu": the sheet's options for Maintain and up, then `menuItems`. A new sheet tool goes in both `trailing` (computers) and `menuItems` (menu items with `sheetMenuItem`) in `GroupSheets`, or in `beforeMenu` if the owner wants it in the row. Phones get `SheetPicker` (a `<select>`) instead of the tabs, and below `lg` Ask AI is the round button in the tabpanel.
- **Panels** use `detailsPanel(full)` and `widePanel` from `src/components/tree/edit/panel.ts`: over the tree on phones (the bottom `PHONE_PANEL_SHARE`; all of it for a form, the chat and Import), beside it from `md`. A new panel uses them.
- **The canvas frames itself** (no `fitView` prop on React Flow: its fit, once cards are measured, undid the framing). Computers fit the sheet after every layout. Below `lg`, a new sheet (the `sheetId` prop) opens at `readableViewport`, later changes keep the view, and `revealViewport` brings the selection into view (`src/components/tree/framing.ts`, unit-tested).
- **Touch:** buttons and menu items get `pointer-coarse:min-h-11` (44 px; an `<a>` needs `flex` or `inline-flex` for it to apply). `globals.css` gives fields 16 px text on touch screens (iPhones zoom into smaller text), outside Tailwind's layers so it beats `text-sm`. A menu that must close on a tap on the canvas listens for `pointerdown`, not `mousedown`: React Flow stops the mouse events browsers make up after a touch.
- On phones, `AppHeader`'s `links` (Members, Settings) and the theme switch move into `UserMenu`. Below `lg` the name beside the initials is `sr-only`, so the button keeps the user's name for screen readers and tests.
- Full-height pages use `h-dvh`, not `h-screen` (100vh reaches under a phone browser's bars).

## ★ Everyone (as built, after the final check)

- ★ Everyone is a built-in first tab, not a stored sheet. `GroupSheets` treats `/s/everyone` (`EVERYONE` in `src/tree/everyone.ts`) as Everyone: the view is `everyoneView(tree)`, `current` stays the first real sheet (the tabs need one), `SheetTabs` gets `everyone` (no sheet options then), `PersonPanel` gets `currentSheetId` `EVERYONE` (adds "Go to" the first sheet showing someone with no sheet of their own), and `ExportItems` gets no `sheetId` (no "this sheet" data). The bar above the tree holds the count and `FindSomeone`, which selects the person and sets the canvas's `focus` (centred by `focusViewport`). A group still opens on its first pinned sheet (`firstSheetId`).
- **Views** (part 2): `ViewSwitcher` in that bar, `EVERYONE_VIEWS` in `everyone.ts` (Tree · Network · Wheel · List). The address holds the view, the Wheel's middle and the selected person (`everyoneHref`: `?view=wheel&centre=&person=`), read with `useSearchParams`; the switcher pushes, a selection replaces. **The address-sync effect reads the view and the middle from the live `window.location`, never from this render's `searchParams`:** a pushed address reaches `useSearchParams` a moment after a state change renders, and an effect using the stale value wrote the old view back (the Wheel's first e2e runs). Keep any address-only value (like the middle) out of React state. Without a view, `chooseView` picks the saved one (`localStorage` `everyone-view`), else List on phones; `shownView` is null until then and nothing is drawn. Opening the Tree or the Network with someone selected sets `focus`, which the canvas keeps as pending until the layout is done.
- **The List:** `EveryoneList` draws `listRows(tree)` (pure, A to Z by the name as written) through `filterRows` (`LIST_FILTERS`; what was typed in the bar's search box, which replaces `FindSomeone` in the List). A fixed-layout table with container queries (`@2xl`, `@4xl`), so the panel beside it counts; narrow, only the person with `relationSummary`. Rows' name buttons are named like cards ("Steve Cruz, 1985"); the selected row has `aria-current` and is scrolled into view. `PersonPanel` gets `onFindInList` everywhere but the List.
- **The Network** (part 3): `NetworkCanvas` (its own React Flow canvas, same props as `FamilyCanvas` plus `tree` and `rootPersonId`) draws `networkGraph(tree)` arranged by `layoutNetwork` (`src/tree/network.ts`, d3-force; ELK took 40 s for 300 people). The arrangement runs only in the browser (an effect, never during the server render), in slices, cached per `GroupTree` and graph in WeakMaps, and the last one stays drawn while a changed group is rearranged. Circles are `data-testid="network-person"`, with buttons named like cards; hearts are named like the Tree's ("Steve Cruz and Arham Chopra, married"). Lines are drawn from the layout's centres (`personReach` stops them at the circle, or below the name), so nodes carry invisible handles only for React Flow. Colours are fixed hex values that read on both themes and in the picture. Its unit tests time 300 and 2,000 people; keep them passing when changing forces. `PersonPanel` gets `onShowInNetwork` everywhere but the Network.
- **The Wheel** (part 4): `kinship(tree, centre)` and `relationName`/`relationPath` (`src/tree/kinship.ts`, pure, unit-tested on the sample and a made-up family), `layoutWheel` (`src/tree/wheel.ts`), `WheelCanvas` (React Flow; a "rings" node behind the people; nodes glide via the `.wheel-canvas` CSS in `globals.css`). Telugu names (the owner's table, in BUILD_PLAN.md part 4) need birth years, sides, the middle person's gender and parallel or cross cousins; change them with their unit tests. The name style is `useNameStyle`/`setNameStyle` (`name-style.ts`, localStorage). People on the wheel are `data-testid="wheel-person"` with their relation in `data-testid="relation"`. `PersonPanel` gets `onShowWheel` elsewhere and `relation` (a `WheelRelation`) in the Wheel.
- **Export:** only drawn views have a picture (`onPicture`/`onPrint` left out of `ExportItems` in the List); a Viewer there has no Export, and `SheetTabs` hides the ⋯ menu when it would be empty.

## Sign-in (as built, step 4)

- `src/server/auth.ts` is the Better Auth instance (`import "server-only"`). Its settings are in `auth-options.ts`, which has no `server-only` so the e2e fixture can build an identical instance (same cookie names and signatures). Base URL and trusted origins come from the pure `authUrls(env)` in `auth-urls.ts`: exact origins only, never `*.vercel.app`.
- Better Auth gets `lazyDatabase()` from `db.ts`: the shared client, not yet connected, so importing `auth.ts` during the build never touches the database. `getDatabase()` connects it.
- Collections `users`, `sessions`, `accounts`, `verifications` (`usePlural: true`); user ids are `ObjectId`s. **Better Auth's Mongo adapter creates no indexes for them** (it only makes those listed in a table's `indexes` option, and its core fields' `unique`/`index` flags are for SQL migrations), so `ensureIndexes` makes them: unique `sessions.token` and `users.email`, `sessions.userId`, `accounts.userId`, `accounts {providerId, accountId}`, `verifications.identifier`, plus TTL on `sessions.expiresAt` and `verifications.expiresAt`. If Better Auth is ever given `indexes` options, use the same keys, or MongoDB refuses the duplicate under another name.
- `src/server/permissions.ts`: `getUser()` (user or null) and `requireUser()` (redirects to `/`). Both read the session with `disableRefresh`, because Server Components can't write cookies; only `/api/auth/get-session` (the user menu's `useSession()`) extends sessions. Route handlers use `getUser()` and answer 401. Don't use `use cache: private` for these: step 5's role must be read fresh.
- `src/proxy.ts` (Next.js 16's middleware) checks only that a session cookie is present, using the pure `proxyDecision()` in `src/server/proxy-rules.ts`. It denies by default: a new public page must be added to `PUBLIC_PATHS` there. Signed-out page loads get a 307 to `/?returnTo=…`; API calls and POSTs get 401.
- `SignInButton` follows Google's branding guidelines (the standard G, Google's light and dark colours); don't restyle it like the app's other buttons.
- The landing page stays static: `SignInButton` reads `returnTo` when clicked and checks it with `safeReturnTo()`. Interactive auth buttons stay disabled until hydrated (`useHydrated()`), so early clicks aren't lost.
- Google sign-in on previews goes through production (Better Auth's `oAuthProxy`, enabled only on Vercel when `OAUTH_PROXY_SECRET` is set).
- Better Auth rate-limits `/sign-in/*` in production builds (3 per 10 s per IP), and the e2e server is a production build: sign in through the `signIn` fixture, not by clicking the button repeatedly.

## Testing conventions

- Unit tests sit next to the code as `*.test.ts(x)` under `src/`, or under `test/`. Vitest uses jsdom by default; pure-logic tests start with `// @vitest-environment node`, and the database config always uses node. `async` Server Components can't be unit-tested in Vitest, so cover them with e2e tests.
- E2E specs live in `e2e/`. Each e2e run gets its own database: `playwright.config.ts` names it, `e2e/global-setup.ts` seeds the sample family into it, the web server gets it as `MONGODB_DB`, and `e2e/global-teardown.ts` removes it.
- Database integration tests are `*.db.test.ts`, run only by `npm run test:db` (`vitest.db.config.mts`). Use `createTestDatabase()` from `@test/db`, which gives each file its own database, and call `drop()` in `afterAll`. The database user can't drop databases, so test databases are emptied collection by collection (`emptyDatabase`).
- `applyOperations` rules go in the pure `planOperations` (`src/server/operations/plan.ts`) and are unit-tested there. The `.db.test.ts` tests cover transactions, persistence, group isolation and role checks (`roleInGroup`, `applyGroupChanges`).
- `test/planning.ts` (`applyPlan`, `sampleState`, `toGroupTree`) applies operations to an in-memory group with the real planner, so edit builders can be tested against the sample family through what the browser draws, without a database.
- `test/fixtures/cruz-young.ts` holds the 36 people from the sample tree image: a same-sex couple, a divorce and remarriage, and in-law parents. It is the shared test data, and the §6 worked examples are its assertions. Import it as `@test/fixtures/...` (tsconfig alias). `test/fixtures/generated.ts` builds large synthetic families.
- `src/app/dev/*` pages (e.g. `/dev/tree`, the layout playground) return 404 unless running `next dev` or built with `ENABLE_DEV_PAGES=1`. Playwright's web server sets that flag, so e2e tests can use them.
- E2E tests save screenshots in `test-results/screenshots/`: `tree.png` (the layout playground; compare with the sample image after layout or card changes), `night-*.png`, `day-tree.png` and `day-sign-in.png` (themes; `docs/screenshots/day-tree.png`, `phone-tree.png` and `phone-panel.png`, shown in README.md, are copies of those screenshots: copy them again after visible changes to the sheets page; `docs/screenshots/everyone-views.png` lays out four of them, `everyone-tree.png`, `everyone-network-chosen.png`, `everyone-wheel.png` and `everyone-list.png`, in a 2×2 grid with captions: after visible changes to ★ Everyone, lay it out again the same way, with a temporary e2e spec that copies of those screenshots feed into `page.setContent` as data URLs, at `deviceScaleFactor: 2` and a 1080 px wide page, then delete the spec), `chat.png` and `night-chat.png` (the assistant), `everyone-tree.png`, `everyone-list.png`, `night-everyone-list.png`, `everyone-network.png`, `everyone-network-chosen.png`, `night-everyone-network.png`, `everyone-wheel.png`, `night-everyone-wheel.png`, `phone-everyone.png`, `phone-everyone-list.png`, `phone-everyone-network.png` and `phone-everyone-wheel.png` (★ Everyone), `phone-tree.png`, `phone-panel.png`, `phone-menu.png`, `phone-chat.png`, `night-phone-tree.png` and `tablet-tree.png` (phones and tablets), `sheet-picture.png` and `sheet-picture-no-photos.png` (exported pictures) and `import-preview.png`. View the relevant ones after UI changes.
- `playwright.config.ts` has three projects: `chromium` (desktop Chrome, every spec except `responsive-*`), `phone` (Chrome's iPhone 13 emulation: 390 × 844, touch) for `e2e/responsive-phone.spec.ts`, and `tablet` (iPad, 810 × 1080) for `e2e/responsive-tablet.spec.ts`. Safari's engine can't be downloaded here. Now and then one phone test runs without touch emulation (`pointer: coarse` doesn't match): its buttons measure their mouse sizes (a 28 px Close, a 40 px sheet picker) and a 44 px check fails, while the other phone tests pass. Rerun before suspecting the change. In phone tests, `tap()` only cards on the screen: Playwright can't pan React Flow, so reach others through the app (a link in a panel). Playwright counts an `sr-only` element as visible.
- `playwright.config.ts` starts three servers: the app's production build (3100), the Cloudinary stand-in (3101) and the Messages API stand-in (3102). No e2e test reaches Cloudinary, Anthropic or Google.
- Signed-in e2e tests use the `signIn(page, name)` fixture from `e2e/fixtures.ts` (import `test` and `expect` from there). It creates a fresh user and session in the run's database with Better Auth's `testUtils` and adds the signed cookie. The app has no test-login route, and ESLint forbids importing `testUtils` under `src/`. `playwright.config.ts` gives the web server `BETTER_AUTH_URL=http://localhost:3100`, a fresh `BETTER_AUTH_SECRET` per run (shared with the fixture through `E2E_AUTH_SECRET`), and placeholder Google credentials; tests stop at the redirect to Google.
- E2E fixtures in `e2e/fixtures.ts`: `signIn(page, name)`, `sampleGroup(owner)` (a group with the sample family and its two sheets) and `addMember(groupId, user, role)`. Use `addMember` when a test only needs a role; `e2e/members.spec.ts` covers the real invite and request flows. Test users' emails are `<name>.<6 hex>@example.com`.
- E2E sections on the dashboard and the members page are `<section aria-label>`, so tests find them with `getByRole("region", { name, exact: true })`.
- No e2e test reaches Cloudinary. `playwright.config.ts` starts `e2e/cloudinary-stub.mts` on port 3101 and points the app at it (`CLOUDINARY_API_URL`, placeholder `CLOUDINARY_*`). It checks signatures like Cloudinary and lists uploads and deletions at `GET /calls` (`E2E_CLOUDINARY_URL`). Tests answer `res.cloudinary.com` photo URLs themselves with `page.route` (see `e2e/photos.spec.ts`).
- In e2e tests, reach pages the way people do (links, Back) as well as with `page.goto`: a full reload hides stale-page bugs. Compare text with `textContent`, not `innerText`, which changes while React moves streamed content into place.
- Playwright scrolls an element into view before clicking or checking it, even one clipped by a scrolling parent, so a menu or popover a person can't see can still pass. For anything that drops down or floats, also check it's the topmost element at its centre (`onScreen` in `e2e/import-export.spec.ts`). The sheet-tab row scrolls sideways (no scrollbar: `scrollbar-none` from `globals.css`; a wheel listener scrolls it, and the open tab is scrolled into view): put new menus outside its scrolling part (`trailing`, or before it like the desktop ⋯, in `SheetTabs`), and keep the tab list `shrink-0` with `whitespace-nowrap` tabs, or Chrome shrinks it and what follows lands on the last tabs.
- In e2e tests, locate inputs with `getByRole("textbox", { name })`, not `getByLabel`. Next.js 16 keeps recently visited pages in the DOM, hidden, and `getByLabel` can match their inputs; `getByRole` skips hidden elements. Filter alerts by text: Next.js's route announcer is also `role="alert"`.
- Chrome's local network check blocks a public page from framing or fetching `localhost`, and it counts `about:blank` and pages made up with `page.route` as public. A test that needs another local origin opens a real local server at `127.0.0.1` (see the framing check in `e2e/security.spec.ts`).
- Locally each save is a transaction plus a re-render against the remote M0 cluster (1–5 s with four workers), so `playwright.config.ts` allows 15 s per assertion and 60 s per test. Wait for the change to appear rather than for a fixed time.
- `samples/` (reference images), `exports/` (the owner's exported files) and `backups/` (`npm run backup`'s output) are git-ignored, so tests and CI must not depend on them, and nothing in them is committed.
- `e2e/security.spec.ts` scans `.next/static` and `.next/server/app` for this run's placeholder secrets (`playwright.config.ts`'s values and `MONGODB_URI`). Give any new secret placeholder a distinctive value and add it there.
